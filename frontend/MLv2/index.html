01 / What this is

A bridge between raw data and ML models

A feature store computes user features once and serves them two ways: in bulk to TRAIN models (offline, PostgreSQL) and one-at-a-time to make real-time predictions (online, Redis).

Same definition on both sides — so a model never sees different numbers in training vs production. That bug is called train/serve skew, and this kills it.

02 / Pipeline

How it works

  1. →Raw CSVSource event & transaction data lands as files.
  2. →IngestionValidate, clean, normalize the raw inputs.
  3. →Feature pipelineComputes all 23 features in batch.
  4. →Dual write, kept in syncPostgreSQL for training · Redis for serving.
  5. →FastAPI RESTServes features over five endpoints.
  6. →ML models consumeA daily scheduled job refreshes everything.

04 / Economics

Why it saves money

01
Compute once, reuse everywhere
Features are computed a single time and reused across every model and team — no duplicated feature engineering.
02
Kills train/serve skew
Eliminates the silent bug that ships wrong predictions and costs hours of debugging.
03
Millisecond serving
Redis serves precomputed features in milliseconds — no expensive recompute per request.
04
Predictable batch cost
Daily batch precompute means predictable, low compute cost vs on-demand recomputation.
05
One source of truth
Faster iteration — and in ML, the real cost is engineer time.
05 / Repository

Source & API

Five REST endpoints expose the stores. The page below calls them live, with a graceful sample fallback when the API is offline.

GET/health — liveness, returns store status
GET/features/online/{user_id} — Redis-first, PostgreSQL fallback (real-time)
POST/features/batch — up to 100 users from the online store
GET/features/offline/{user_id} — PostgreSQL only (training lookups)
GET/features/metadata — the 23-feature catalog from the registry
